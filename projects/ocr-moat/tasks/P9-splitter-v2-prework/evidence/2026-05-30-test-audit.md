# Resplit Money-Math Test Audit + Fix-First List (P9.2)

> Source: prework workflow `w5o5plp2k` test-audit agent. The safety net we plan a V2 change against.

## Headline

The money engine is **NOT** an MVP — it has property-based testing (10k random receipts/run, fixed seed), a full invariant lattice (ZERO_SUM / BOUNDED / PROPORTION_BOUNDED / REMAINDER_DETERMINISTIC), settlement FX conservation, and orphan-handling contracts. **No money-math test is disabled** (the 4 XCTSkips are UI-precondition guards). The gaps are at the *edges* the new receipts expose: NaN/Inf, negative amounts, no-decimal/3-decimal rounding inside the engine, and post-tax/custom-tip end-to-end.

## Fix-FIRST (before ANY V2 change)

- **[Engine NaN/Inf hardening + test]** ReceiptSplitEngine.calculateSplit (ReceiptSplitEngine.swift:26-41,44) has no guard against .nan/.infinity item amounts; a single poisoned amount silently nullifies every BOUNDED/PROPORTION assertion (they compare-false).
  - Action: Add an engine-level test feeding a NaN and an infinite item amount through calculateSplit and asserting the result is finite + still satisfies MathInvariants (or documents an explicit reject path). Pin the chosen behavior BEFORE any V2 engine rewrite touches the division loop.
- **[Negative-amount BOUNDED contradiction]** SplitEngineEdgeCaseTests.swift:38-69 proves the engine returns proportion 1.25 / -0.25 and negative amountOwed for a negative (discount) item — a direct violation of the BOUNDED and PROPORTION_BOUNDED contracts in MathInvariants.swift:57,82-107 that is never run through the lattice.
  - Action: Decide and pin the contract: either clamp/handle negative line items in the engine, or formally relax BOUNDED for discount items. Add a MathInvariants-gated negative-item scenario so the contract and the behavior stop contradicting each other. This is load-bearing for V2 because real receipts have comps/discounts.
- **[Post-tax + custom tip end-to-end through settlement]** calculatePostTax==true and .custom tip are only unit-tested at the calculatedTip helper; neither is driven through ReceiptSplitCalculator.updateSplits -> SettlementService, so their effect on per-participant balances and settlement ZERO_SUM is unverified (TaxTipEdgeCaseInvariantsTests.swift:308 uses pretax only).
  - Action: Add two end-to-end tests (post-tax tip receipt, custom-amount tip receipt) that settle and assert SETTLEMENT_ZERO_SUM + correct per-person balances, before V2 changes the tip/total pipeline.
- **[ReceiptTotalCalculator overflow guard]** calculatedTotal (ReceiptTotalCalculator.swift:5-20) sums itemSum+tax+tip+custom with no bound check; documented as a live production gap at TaxTipEdgeCaseInvariantsTests.swift:32-37. A corrupt OCR tax/total flows into the engine unflagged.
  - Action: Ship a sanity threshold (e.g. flag total > k x subtotal) and a test pinning it, OR consciously bless the no-guard behavior in a test, before V2 alters total composition.
- **[Cross-target MathInvariants duplication]** UITestDataCorpusInvariantTests.swift:14-18 re-implements ZERO_SUM/BOUNDED/PROPORTION inline because MathInvariants lives in the ReceiptSplitterTests target and is not linked into ResplitCoreTests. Two copies of the invariant math can drift apart silently.
  - Action: Promote MathInvariants into a shared test-support target (or the ResplitCore test-support layer) so the corpus sweep and the engine suites assert the identical contract. Do this before V2 so both surfaces move together.

## Coverage gaps

- **[high]** NaN / infinite item amount through the engine — ReceiptSplitEngine.calculateSplit (ReceiptSplitEngine.swift:26-41) divides item.amount by participant counts with NO guard against amount being .nan or .infinity. A NaN amount poisons rawAmountsByEach, makes sumOfRawAmounts NaN, every proportion NaN, and the BOUNDED/PROPORTION_BOUNDED asserts compare-false silently. The property test generator only ever produces 0.01...100.0 finite amounts (PropertyBasedEngineInvariantsTests.swift:97). FXInvariantsTests/ReceiptConversionSnapshotTests pass .infinity only into stampConversion, never into the split engine. Zero engine-level NaN/Inf coverage.
- **[high]** Negative-amount item run through the engine invariant lattice (BOUNDED / PROPORTION_BOUNDED) — SplitEngineEdgeCaseTests.negativeItemAmountProducesNegativeSplit (SplitEngineEdgeCaseTests.swift:38-69) PROVES the engine yields proportion 1.25 for alice and -0.25 for bob and amountOwed -$10 for bob — which directly violates BOUNDED (owed>=-0.01 at MathInvariants.swift:57) and PROPORTION_BOUNDED (0<=p<=1, sum~1 at MathInvariants.swift:82-107). Yet this scenario is NEVER fed through MathInvariants.assertAllEngineInvariants. The invariant corpus (ReceiptSplitEngineInvariantsTests, PropertyBased, StateMachine) uses only non-negative amounts, so the documented contract and the documented actual behavior contradict each other with no test forcing a resolution. A discount/comp line item (real receipts have them) lands here.
- **[medium]** Post-tax tip end-to-end through engine->settlement (calculatePostTax == true beyond the pure tip helper) — calculatePostTax==true is exercised only at the SummaryItemCalculator.calculatedTip unit level (SplitEngineMoneyLossTests.swift, SummaryItemCalculatorTests, SplitEngineEdgeCaseTests). TIP_EDIT_INVALIDATES_CACHE (TaxTipEdgeCaseInvariantsTests.swift:308) and every settlement/fingerprint test use pretax tip only. No test drives a post-tax-tip receipt through ReceiptSplitCalculator.updateSplits -> SettlementService, so the post-tax path's effect on per-participant balances and settlement ZERO_SUM is unverified.
- **[medium]** Custom-tip ( .custom / nil tipOption, and arbitrary customAmount ) in settlement and total — TIP_INVARIANT and TaxTip suites early-return on .custom (MathInvariants.swift:125, UITestDataSummaryInvariantTests.swift:67). calculatedTip returns nil for .custom (SummaryItemCalculator.swift:18). No test verifies that a hand-entered custom tip flows correctly into resolvedTotalAmount -> engine -> settlement and still satisfies ZERO_SUM, despite custom tip being a primary user path.
- **[medium]** Total-overflow / total >> subtotal sanity (ReceiptTotalCalculator) — Self-documented in TaxTipEdgeCaseInvariantsTests.swift:32-37: ReceiptTotalCalculator.calculatedTotal (ReceiptTotalCalculator.swift:5-20) sums itemSum+tax+tip+customExtras with NO bound check. A corrupt OCR tax of e.g. $9,999 on a $20 subtotal produces a total that flows into the engine and settlement unflagged. It is labeled a production gap; there is no test pinning any threshold because none exists in production.
- **[medium]** Live-sync vs engine rounding reconciliation (the documented 1-cent divergence) — LiveSyncSumRoundTripInvariantsTests pins that live-sync (round(amount/N)) and the engine (proportional + tail-remainder to sorted-first) DISAGREE by up to N cents (e.g. 3-way $100: engine 100.00, live-sync 99.99). Both formulas are pinned but nothing tests that a receipt edited live then settled produces a self-consistent total — the divergence is frozen, not resolved, so a live-then-final receipt can show two different per-person numbers with no test catching the user-visible mismatch.
- **[low]** Orphan items inside a LIVE session (claimedShareCents path) — Engine orphan handling (sharedEqually==false && empty participantIds excluded from distributable pool) is heavily tested. The live-sync surface (LiveSessionItem.claimedShareCents) is only tested for sharedEqually==true items (LiveSyncSumRoundTripInvariantsTests.swift:39-49). There is no test for how an unclaimed/orphan item behaves in a live session sum, so live-sync orphan parity with the engine contract is unverified.
- **[low]** Zero-decimal (JPY) and 3-decimal (BHD) minor-unit ROUNDING inside the split engine itself — The engine hardcodes 2-decimal cents rounding ( *100 .rounded() /100 at ReceiptSplitEngine.swift:73,78). JPY/BHD are tested for FORMATTING (SplitEngineMoneyLossTests.swift:9-50) and for settlement FX (MultiCurrency tests), but no test runs a JPY or BHD receipt through calculateSplit to confirm the 2-decimal remainder distribution doesn't introduce sub-yen artifacts on a JPY split. The Japan fixture (UITestDataJapanMidSplitTests) checks item sums, not engine split rounding.
