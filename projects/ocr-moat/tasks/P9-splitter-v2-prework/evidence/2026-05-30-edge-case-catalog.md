> Source: prework workflow `w5o5plp2k` — 12 cataloger agents + 12 adversarial verifiers. 102 edge cases across 12 dimensions. Adversarial: 3 rejected, 20 need revision. **LIVING DOC — strengthens as more receipts arrive. PLANNING ONLY, no code.**

## multi-currency-resolution

_The V1 splitter resolves currency in TWO disconnected places with very different competence, and the splitter math itself is currency-blind. (1) The V4 OCR happy path, OCRSnapshotMapper.resolveCurrency (OCRSnapshotMapper.swift:83-149), is actually decent: it prefers Azure's ISO currencyCode, then disambiguates an ambiguous symbol via MerchantAddress.countryRegion, then symbol-default, then folder default. But its disambiguation tables are narrow and the symbol-default tier (Currency.inferCurrencyCode, Currency.swift:52-98) unconditionally maps $->USD and Yen->CNY whenever a country is absent or unmapped. (2) The V3 reconciler shim (V3ReceiptReconciler.swift:76-77) hardcodes currencyCode:nil / currencySymbol:nil, throwing away currency entirely before reconciliation. (3) Reconciler.matchThreshold is a hardcoded 0.01 (Reconciler.swift:34) with no zero-decimal (JPY/KRW/VND) or cash-rounding awareness. (4) Three independent USD/$ fallbacks (Receipt.effectiveCurrencyCode->USD Receipt.swift:306; ReceiptSplitCalculator tip display ?? USD :90; model symbol ?? $ Receipt.swift:217) mean a receipt that fails resolution silently formats every per-head amount in USD with a $ glyph. CRITICAL CONTEXT: corpus.jsonl is 47/48 un-scanned stubs; only Marathon Cafe (USD/$, CountryRegion USA) is fully parsed. So international evidence is the P8 V1-misses story + the i18n investigation (ocr-i18n-edge-cases-2026-05-30.md), naming real RM/AED/AUD/GST-inclusive/deposit receipts in Leo's Photos. The splitter never mis-DIVIDES on currency (proportions are pure ratios) but it mis-LABELS and mis-RECONCILES, a real misbill the moment two people from different-currency trips compare what they owe, or when an FX conversion multiplies a wrong base code._

### [P1] · Symbol-only receipt with no CountryRegion: $ unconditionally becomes USD (CAD/AUD/SGD/MXN/NZD/HKD all collapse to USD)
- **Surface / apportions:** currency-fx · excluded-from-split
- **Receipt:** i18n investigation ocr-i18n-edge-cases-2026-05-30.md:17-23 and :52-53 cite Mexican $450 MXN resolving as USD (~18x FX error) and Canadian/Australian $ as USD. P8 misses story line 36 names real RM, AED, AUD receipts in the corpus. The one fully-parsed corpus row (Marathon Cafe, $/USD/CountryRegion=USA) only works because Azure returned both currencyCode USD AND CountryRegion USA; the moment either is absent, the symbol-default tier fires.
- **V1 now:** OCRSnapshotMapper.resolveCurrency only disambiguates an ambiguous symbol when MerchantAddress.countryRegion is present AND in the narrow map (OCRSnapshotMapper.swift:103-114). With no country it falls to the symbol tier (:116-125) calling Currency.inferCurrencyCode, hardcoding case $: USD (Currency.swift:54-55). CountryRegion is parsed (AddressValueV4.countryRegion, ReceiptResultV4.swift:108) but only consulted for ambiguous symbols, and Azure frequently returns it nil for non-US receipts.
- **Mis-bill risk:** A guest on an Australian or Canadian trip whose receipt has a $ symbol but no country gets tagged USD. If they then run FX conversion (Receipt.displayedAmount, Receipt.swift:326-329) the wrong base code multiplies every per-head amount by the wrong rate; or if displayed raw, AUD 120 reads as $120 USD. Every participant on that receipt sees a mislabeled and (post-conversion) mis-scaled share.
- **Direction:** PLAN: make the symbol-default tier for AMBIGUOUS symbols ($, Yen, kr) return nil instead of a guess, so resolution falls through to countryRegion -> folderCurrencyCode -> device region rather than silently committing USD. Preserve the invariant: an ambiguous symbol must never out-rank a country or folder signal (i18n doc P0 rule :68-69). Keep unambiguous symbols (Euro/Pound/Won/R$) resolving exactly as today. Surface a low-confidence currencySource so the UI can prompt instead of presenting a confident wrong code.
- **Needs test:** Extend CurrencyCountryDisambiguationTests: testDollarWithNoCountryFallsBackToSymbolDefaultUSD currently ASSERTS USD (line 70) -- invert it to assert nil/folder/device fallback once ambiguous-symbol-without-country no longer auto-commits USD; add testDollarAUDFolderBeatsSymbolDefault and testDollarCADNoCountryDoesNotForceUSD.

### [P2] · Reconciliation tolerance is USD-only 0.01 -- wrong for zero-decimal (JPY/KRW/VND) and cash-rounded currencies
- **Surface / apportions:** splitter-core · excluded-from-split
- **Receipt:** P8 misses story line 36 explicitly: matchThreshold = 0.01 ... wrong off-USD. The i18n doc :89-93 specifies the correct rule: tolerance(currency) is 0.05 cash-rounded, 0 zero-decimal, 0.01 else, citing JPY/KRW/VND/CLP zero-decimal and rounding adj $0.01 (P8 story line 22) cash-rounding receipts in the corpus.
- **V1 now:** Reconciler.matchThreshold and warnThreshold are hardcoded Doubles 0.01 / 0.05 (Reconciler.swift:34-35) applied identically in sumOfItemsFinding (:63) and totalFinding (:80) regardless of currency -- and currency is nil anyway from the V3 shim.
- **Mis-bill risk:** A JPY receipt where subtotal+tax+tip = total exactly in whole yen can still trip a 0.01 delta from float artifacts -> false totalMismatch error surfaced to the user, eroding trust; conversely a cash-rounded CHF/AUD receipt with a legitimate 0.05 rounding line passes the 0.01 gate and reconciles as clean when it actually carries an unmodeled rounding adjustment that shifts the payer's residual.
- **Direction:** PLAN: replace the constant with a tolerance(forCurrency:) lookup -- 0 for zero-decimal codes (JPY/KRW/VND/CLP), 0.05 for cash-rounded, 0.01 default (i18n doc :89-93). Requires the currency-threading fix above to feed it a code. Invariant: the existing USD corpus must reconcile identically (default 0.01 unchanged). This governs reconciliation labeling only, not apportionment.
- **Needs test:** Add ReconcilerTests.testZeroDecimalCurrencyUsesIntegerTolerance (JPY receipt, whole-yen balance, asserts clean not totalMismatch) and testCashRoundedCurrencyTolerance.

### [P3] · Mixed-currency receipt: single receipt prints two currencies (dual-total / duty-free / FX-on-receipt) and the model holds only one code
- **Surface / apportions:** currency-fx · excluded-from-split
- **Receipt:** The i18n doc regression-fixture list names dutyfree_dual_total (:109) and CAMBIO-as-total / dual-total cases (:53, es row), plus the P8 story total != balance due deposit class (line 25, catering check total $2180.26 vs balance due $1918.26) which is the same shape: two monetary figures on one receipt where the engine must pick the right one. Duty-free and border receipts routinely print local + USD.
- **V1 now:** OCRSnapshot/Receipt carry exactly one currencyCode + one currencySymbol (Receipt.swift:38-39); resolveCurrency reads only fields.total.valueCurrency (OCRSnapshotMapper.swift:87,103,116) -- there is no concept of a second currency or of which printed total is authoritative. resolvedTotalAmount precedence (Receipt.swift:265-280) picks a number but is currency-agnostic, so it can select a figure denominated in the OTHER currency.
- **Mis-bill risk:** On a dual-currency receipt the engine may scan the USD courtesy-total but tag it with the local symbol (or vice versa), so the distributable pool is a number in one currency labeled as another. - **Direction:** PLAN: detect dual-total receipts (two currency-typed Total candidates with different codes) and pin the AUTHORITATIVE total to the one whose currency matches the resolved currencyCode; if ambiguous, prompt rather than guess. - **Needs test:** Add a fixture test (dutyfree_dual_total) asserting the chosen total and the resolved currencyCode are the same denomination, and that a local+USD dual receipt does not feed the USD figure into a local-currency split.

- **Surface / apportions:** currency-fx · proportional-by-consumption

## no-decimal-currencies

_Resplit V1's entire money pipeline hardcodes a 2-minor-unit (cents) model: the split engine rounds with `(value * 100).rounded() / 100` (ReceiptSplitEngine.swift:73,78), the OCR reconciler compares against a fixed `matchThreshold = 0.01` (Reconciler.swift:34), the V3 shim passes `currencyCode: nil` (V3ReceiptReconciler.swift:76) so the reconciler can NEVER learn the receipt is JPY/KRW/VND/CLP, the `isMoney` regex requires a literal `\.\d{2}` two-decimal tail (Currency.swift:29), and tip is computed as a raw `base * pct/100` with no whole-unit rounding (SummaryItemCalculator.swift:22). For 0-minor-unit currencies (JPY, KRW, VND, CLP) every one of these is wrong: 1 yen is the atomic unit, so a 0.01 threshold is ~100x too tight (false reconciliation chips on legitimate whole-yen rounding), the split engine mints unpayable fractional yen, and 1,200 yen risks being read as 12.00 by the decimal-tail gate. Display via formatCurrency (Double.swift:49-52 FloatingPointFormatStyle.Currency(code:)) and manual-entry fractionDigits (ManualExpenseSheet.swift:236-243) DO correctly derive 0 digits from the code, so the bug is in the math/reconcile/OCR-parse layers, not the renderer, which makes it silent: amounts LOOK right while the stored Double carries phantom fractional units that won't reconcile and split unevenly. EVIDENCE CAVEAT: the 48-receipt corpus is 19 USD-tagged plus unset, containing ZERO native JPY/KRW/VND/CLP receipts, so the strongest in-corpus anchor is Marathon Cafe (Little Neck) USD (subtotal $49.45, tax $4.39, tip $7.42, 3% CC fee $1.77) which proves the 2-decimal pipeline end-to-end; the no-decimal cases are projected from that pipeline plus the P8 what-V1-misses story which names no-decimal currency as edge case #6 (matchThreshold = 0.01 wrong off-USD) and the symbol table (Currency.swift:64-69) that already maps won to KRW, dong to VND, and country CL to CLP, JP to JPY. PLAN ONLY: every direction names the invariant it must preserve and the protective test it needs; no code proposed._

### [P1] 🟡 Split engine mints unpayable fractional minor units via hardcoded *100 cents rounding
- **Surface / apportions:** splitter-core · proportional-by-consumption
- **Receipt:** Pipeline anchor: Marathon Cafe split of $63.03 across N diners lands on clean cents because USD rounds to 1/100. Project that math onto a 10,000 yen bill split 3 ways: ReceiptSplitEngine produces 3333.33 / 3333.33 / 3333.34, where .33 is a phantom (yen has no sub-unit). P8 story #6 flags no-decimal currency as a known V1 miss; symbol table Currency.swift:64-69 maps won to KRW and dong to VND, confirming these currencies are in-scope.

## three-decimal-currencies

_Resplit V1 silently assumes every currency has 2 decimal places (100 minor units). For BHD / KWD / OMR / TND — the four ISO-4217 currencies with 1000 minor units (3 decimals: fils / baisa) — the DISPLAY layer is partly correct (CurrencyAmountFormatter and ManualExpenseSheet derive fraction digits from Foundation's per-currency minor units, and SplitEngineMoneyLossTests.swift:15-19,47-50 actually pin BHD at 3 digits), but the MATH/RECONCILE/INVARIANT layers are hardwired to cents. The split engine rounds via `(value*100).rounded()/100` and uses a `0.005` penny-remainder threshold (ReceiptSplitEngine.swift:73,78-79); the ZERO_SUM tolerance is `±0.01` (ReceiptSplitCalculator.swift:159, MathInvariants.swift:36); the OCR reconciler match/warn thresholds are `0.01`/`0.05` (Reconciler.swift:34-35); and the V3 adapter throws away currency entirely with `currencyCode: nil` (V3ReceiptReconciler.swift:76). In a 1000-minor-unit currency these constants are all 10x too coarse: 0.01 BHD = 10 fils, not one. The corpus proves how invisible this is — all 48 dining receipts are USD/USA (parsed Currency=USD, CountryRegion=USA on the one document-typed record; zero dinar/fils/baisa markers across all 48 raw OCR contents), so no regression test or capture exercises the path. The two evidence docs only flag foreign currency obliquely: 2026-05-30-what-v1-splitter-misses.md line 36 ("No-decimal & foreign currency (RM, AED, AUD) — V3ReceiptReconciler hardcodes currencyCode: nil and matchThreshold = 0.01, both wrong off-USD") and the Azure gap report's P3 row (CountryRegion → currency inference, NOT PARSED). RM/AED/AUD are all 2-decimal; the THREE-decimal case (BHD/KWD/OMR/TND) is strictly worse and is the case nobody named. Net misbill: in a 3-decimal currency the engine truncates each share to the nearest 10 minor units and dumps a remainder of up to ~9 fils onto the lexicographically-first participant, while the ZERO_SUM invariant — which is supposed to be the safety net — passes a leak of up to 9 minor units because its tolerance is itself 10x too loose. The OCR reconciler simultaneously goes blind (a 9-fils OCR error is below its 0.01 floor) AND noisy (legit 3-decimal totals that don't round to cents trip false totalMismatch warnings). Tip-base and proportional tax/extras inherit the same cent-rounding skew. Direction is plan-only: thread the receipt's effectiveCurrencyCode + its minor-unit exponent (10^digits) into the engine, reconciler, and invariants so rounding granularity and tolerances scale to the currency instead of being frozen at 1/100._

## fx-cross-currency-settlement

_Resplit V1 only does FX at the FOLDER level (SettlementService.multiCurrencyFolderSettlement, SettlementService.swift:235-367). The single-receipt path (calculateSettlement(for: ReceiptDTO), :40-68) has NO conversion at all — it returns amountOwed verbatim in receipt.currencyCode. The folder converter multiplies receiptTotal*rate and amountOwed*rate (lines 319-327) but NEVER rounds the result to the base currency's minor units; converted transactions carry full-precision Doubles, only loosely guarded by accuracy:0.02 in tests (SettlementServiceMultiCurrencyTests.swift:229,232). Rate source is the resplit-currency-api worker via ResplitCurrencyProvider with a layered fallback: canonical /quote -> canonical /history -> dated snapshot -> prior-day lookback (FXRateProvider.swift:240-272, 717-851). Inverse-rate fallback exists only inside the snapshot decoder (1.0/inverse, :964-968) and cross-rate through a third base (toBase/fromBase, :973-979) — both introduce asymmetric rounding and a wrong-direction money error if a currency code is misidentified upstream. The corpus has only 1 OCR'd receipt (Marathon Cafe, USD), so cross-currency receipt evidence is drawn from the P8 V1-misses story (RM/AED/AUD, service tax 6%=3.84, 10% service charge=RM26/$29.93/6.40) and the verified ocr-i18n investigation (Tokyo yen->CNY 20x, Mexican $->USD 18x, Thai BE-year future-dating, zero-decimal JPY/KRW, R$/RM/S$ multi-char symbols dropped). Secondary classes: no minor-unit rounding after conversion (phantom JPY cents, BHD millièmes truncated), policy:.latest re-pricing historical trips at today's rate (:253), and same-day snapshot-reuse gate (:268) that re-fetches a different rate on recompute and silently re-bills._

## tax-multi-and-on-tax

_Resplit's splitter has a single scalar tax slot end-to-end. At the OCR boundary `ScannedReceipt.tax` SUMS every `.tax` extra into one number (ScannedReceipt.swift:36-46); the OCRSnapshotMapper only ever reads Azure's collapsed `TotalTax` and never `TaxDetails[]` (OCRSnapshotMapper.swift:49); `OCRSnapshot` has one `tax: Double?` (OCRSnapshot.swift:33); `Receipt.taxItem` is `summaryItems.first(where type==.tax)` (Receipt.swift:256-258); and `ReceiptTotalCalculator` reads one `taxItem.amount` (ReceiptTotalCalculator.swift:10). The splitter's domain enum `SummaryItemType` is only {subtotal,tip,tax,total,custom} (ReceiptItemsFixer.swift:444-450) — there is NO per-tax-line, no serviceCharge, no inclusive-tax, no second-tax concept. So for the WHOLE class of multi-tax / tax-on-tax / per-item-tax receipts the V1 engine works on a number it can never reconstruct correctly. The split math itself (proportional-by-consumption) is actually CORRECT for tax in the common case — tax rides inside totalAmount and is spread by each person's item share — so the failure mode here is almost never "wrong apportionment of a correct tax", it is "the tax FIGURE fed to the engine is wrong/incomplete", which then mis-bills everyone proportionally. Two sub-classes are genuinely apportionment bugs, not figure bugs: (a) inclusive (GST-included) tax double-counts the total and over-bills everyone; (b) per-item differential tax (alcohol vs food) is apportioned by total consumption instead of by who drank, so non-drinkers subsidize drinkers' higher tax. Real receipts in the corpus and P8 story prove every case: Marathon Cafe (USD, two money-classes Tax $4.39 + a separate 3% CC fee $1.77 that V1 drops), the catering check (sales tax + admin $80.83 + auto-grat $339.47 + deposit -$262 where total $2180.26 != balance due $1918.26), service tax 6%=$3.84 alongside sales tax (Malaysian receipt), and "GST included in total $90.68". All directions are PLAN ONLY and gated on the 2.0 freeze + Leo sign-off per P8 Constraints._

### [P2] · Per-item differential tax (alcohol taxed higher than food) apportioned by total consumption
- **Surface / apportions:** splitter-core · item-level
- **Receipt:** Many US jurisdictions tax alcohol at a higher combined rate than food (e.g. prepared-food vs liquor/excise). - **V1 now:** V1 has ONE tax scalar for the whole receipt (OCRSnapshot.swift:33, ReceiptTotalCalculator.swift:10). INVARIANT to preserve: assertZeroSum (Σ per-item-taxed shares + orphans == total ±0.01) AND assertBounded (no negative shares); the per-item tax must still sum to the receipt's total tax exactly.
- **Needs test:** New invariant test: a 2-person receipt where A claims $100 alcohol (10% liquor tax = $10) and B claims $100 food (4% food tax = $4) must bill A's tax = $10 and B's tax = $4, NOT the blended $7/$7 the current pool produces; assert Σ item-level taxes == total tax and assertZeroSum.

## tax-inclusive-vs-exclusive

_V1's entire money model is `subtotal + tax + tip + customExtras = total` (ReceiptTotalCalculator.swift:19), where `tax = receipt.taxItem?.amount.valueToUse` is ADDED UNCONDITIONALLY (line 10) with no inclusive-vs-exclusive distinction anywhere in the codebase. Grep for `inclusive|taxInclusive|priceIncludesTax|VAT|GST` across the entire iOS tree (excluding worktrees) returns ZERO tax-related hits — the only "inclusive" matches are date-window and tolerance comments. Neither domain enum encodes the concept: `SummaryItemType = {custom, tip, tax, total, subtotal}` (ReceiptItemsFixer.swift:444-449) and `ScannedExtraKind = {tax, tip, fee, serviceCharge, mandate, surcharge, discount, credit, unknown}` (ScannedReceipt.swift:118-127) both lack any `inclusive` flag. The OCR mapper (OCRSnapshotMapper.swift:48-49) maps `subtotal` and `totalTax` independently and never checks whether the printed total already equals subtotal (the tell-tale of tax-in-price). NET CONSEQUENCE: when a VAT/GST-inclusive receipt is scanned, the line-item prices already contain the tax, AND the printed tax line gets captured as a `.tax` summaryItem, so `calculatedTotal` re-adds it on top of an item sum that already includes it — a systematic double-add equal to the full tax amount. The P8 V1-misses story names this directly: "GST included in total $90.68" needs "an `inclusive` flag, not an additive `.tax`" — V1 has neither. The single fully-decoded corpus receipt (Marathon Cafe, id d49d7331c4d0) is the EXCLUSIVE-tax happy path (Subtotal $49.45 + Tax $4.39 = Bill Total $53.84) that V1 handles correctly, which makes the inclusive case invisible in testing — no `TaxTipEdgeCaseInvariantsTests` case covers inclusive/GST/VAT. The reconciler compounds this: `totalFinding` computes `expected = subtotal + positives - negatives` with `.tax` always in `positives` (Reconciler.swift:70,78), so an inclusive receipt where `total == subtotal` throws a spurious `totalMismatch` of exactly the tax amount. And the engine's `* 100 / 100` cents rounding (ReceiptSplitEngine.swift:73,78) plus the reconciler's USD-cent `matchThreshold = 0.01` (Reconciler.swift:34) bake in a 2-decimal assumption that mis-rounds inclusive-tax math on 0-decimal (JPY) and no-decimal-symbol (RM/AED) international receipts where inclusive GST/VAT/SST is the norm. The fix surface is concentrated: an inclusive flag at the scan layer (ScannedExtra) that propagates to ReceiptTotalCalculator so inclusive tax is EXCLUDED from the additive total (it's already in itemSum), plus a tip-base correction so percent-tip isn't computed on a tax-inflated base._

## rounding-money-loss

_The Resplit V1 engine does ALL money math at exactly 2 decimal places: `ReceiptSplitEngine.swift:73` rounds every share via `(proportion * distributableAmount * 100).rounded() / 100` and `:78` computes the leftover remainder the same way, then `:79-81` dumps the entire penny remainder onto `sortedIds.first` (lexicographically-first stableId). The sum-round-trip invariant is enforced loosely at ±$0.01 (ZERO_SUM, ReceiptSplitCalculator.swift:159 / MathInvariants.swift:36). This 2-decimal assumption is hardcoded and currency-blind: the engine never consults `receipt.currencyCode`, so for no-decimal currencies (JPY/KRW/VND) it can mint fractional units that do not exist, and for the cash-rounded currencies on Leo's actual trips (MYR ringgit, AUD, CHF) it ignores the 5-sen/5-cent/Rappen rounding the merchant already applied — the printed total and Resplit's recomputed total disagree, and the gap lands silently on one diner. Four concrete corpus receipts anchor this: (1) Marathon Cafe Little Neck — subtotal 49.45, tax 4.39, +3% CC fee 1.77, tip 7.42, total 63.03 — every figure is cent-level and the remainder logic is load-bearing here; (2) Lowe's — total 10.86 on a 5-way mulch split would give 2.172/head, rounded to 2.17×5=10.85, leaving a 1¢ remainder always paid by one person; (3) Fuzí Pasta — 285.75 sub, 25.36 tax, 62.22 tip, 373.33 total across a large party is exactly the high-headcount accumulation case where per-head rounding drift compounds; (4) the P8 story's MYR/AED/AUD receipts + "rounding adj $0.01" line + "GST included in total $90.68" prove off-USD and cash-rounding receipts are already in Leo's photo roll. The whole dimension is currently UNTESTED for anything other than USD cents — there is no minor-unit table, no cash-rounding step, and the remainder-recipient is deterministic but unfair (always the same person eats it across every receipt in a folder)._

### [P1] 🟡 No-decimal currency mints sub-unit pennies that don't exist (JPY/KRW/VND)
- **Surface / apportions:** splitter-core · proportional-by-consumption
- **Receipt:** P8 story 2026-05-30-what-v1-splitter-misses.md line 36 explicitly flags 'No-decimal & foreign currency (RM, AED, AUD)'; the iOS Currency.swift:65,130 already maps ₩→KRW and JP→JPY and OCRSnapshotMapper.swift:99 calls out '¥→JPY' Tokyo receipts. The engine never reads receipt.currencyCode; there is no minor-unit lookup anywhere in ReceiptSplitter/.

- **Needs test:** MathInvariants.assertZeroSum re-parameterized by minorUnitDigits — assert Σ shares == total to the currency's minor unit (±1 minor unit, not ±$0.01), plus a new assertNoSubUnit: every amountOwed is an integer multiple of 10^-digits for the receipt currency. Fixture: ¥10000 / 3 participants must yield {3334,3333,3333} summing to exactly 10000.
- **Adversarial [needs-revision · P1]:** Core defect is REAL and verified: ReceiptSplitEngine.swift:73/:78 hardcode `*100/.../100` and never read receipt.currencyCode (grep confirms the only currencyCode use is the display path in ReceiptSplitCalculator.swift:90); Currency.swift maps ₩→KRW/JPY/VND (lines 65,130) but has NO minor-unit table; Double.swift:50 uses FloatingPointFormatStyle.Currency(code:) which DOES respect locale minor units, so the engine-vs-display mismatch (¥3333.33 engine → ¥3333 display, ¥1 vanishes) is mechanically plausible. P8 story line 36 'No-decimal & foreign currency (RM, AED, AUD)' is real verbatim. BUT the fix is under-specified and risky: it must touch the DISTRIBUTABLE pool only (orphans + tax/tip already fold into totalAmount upstream), and for 0-digit currencies the remainder line at :78-81 must distribute whole minor units or it will violate the new assertNoSubUnit on the very first JPY fixture. ## item-level-shared-modifiers

_V1 models every receipt row as ONE atomic line: ReceiptItemDTO carries only {amount, sharedEqually, participantIds} (ReceiptItemDTO.swift:3-19) — no quantity, no unit price, no modifier linkage. The engine can only do three things with a row: split it equally across ALL participants, split it evenly across the listed claimers, or orphan it (payer eats it) — ReceiptSplitEngine.swift:26-41. This breaks down on EVERY real-world item shape that isn't "one indivisible dish one person ate." Concrete corpus evidence: Ishq "Naan Plain qty 2 = $12.00" and Fuzí Pasta "Simple Pasta qty 4 = $88.00 / Sangria qty 4 = $40.00 / Gelato Hazelnut qty 2 = $10.00" are multi-unit lines that can't be allocated per-unit; Lowe's "2-CU FT MULCH qty 5 = $10.00" carries an embedded "5 @ 2.00" multiplier line that qwen hallucinated into a phantom $2.00 second item; Marathon Cafe's items wrap onto multiple lines with parenthetical modifiers "(Half)(W. Soup Of The Day)" that Azure glued into the name; the P8 story documents shared appetizers ("chowder fries / salads among the table"), modifier sub-items ("caesar salad / add chicken"), and comped $0.00 items (ice water ×2, comped mushroom/pancake) that V1 has no concept of. There is NO quantity-aware split path in the engine, the qty-explode helper (SplitItemUseCase.swift) has rounding + assignment-inheritance bugs, quantity is Int? so weighted per-lb/kg lines are coerced to 1 (OCRSnapshotMapper.swift:71), the engine cent-rounds regardless of currency (ReceiptSplitEngine.swift:73), and negative/comp/void lines trip a zero-split guard that silently dumps the whole bill on the payer (SplitEngineMoneyLossTests.swift:151-176). The cross-cutting invariant V2 must add: a line's allocatable amount = unit_price × allocated_quantity, with Σ(allocated units) ≤ line quantity and the line's full price still reconciling into the receipt total (zero-sum) regardless of how the units are spread._

## last-mile-parse-fidelity

_This dimension covers the gap between what's printed on a receipt and what Azure prebuilt-receipt actually hands the splitter — and the fact that V1 has no "verify before you split" gate keyed to OCR confidence. Grounded in the P7 multi-model benchmark embedded in corpus.jsonl (records 0-3: Marathon Cafe, Lowe's, Fuzí Pasta, Ishq), the Azure v4 gap report, and the V1-misses story.

The seven edge cases below cluster around one structural fact, confirmed in code: the production decode path (OCRSnapshotMapper.map, OCRSnapshotMapper.swift:36-52, reading only FieldsV4.subtotal/totalTax/tip/total at ReceiptResultV4.swift:55-77) collapses the receipt to subtotal+tax+tip+total and DROPS every other line. Azure already returns more — per-word confidence, and FieldsV4 has slots — but TaxDetails[] and Payments[] are not even in the decoder. The strongest single piece of evidence: on Marathon Cafe (corpus id d49d7331c4d0), Azure returns total=53.84 (the printed "Bill Total" = subtotal+tax) and drops the printed "3% credit card processing fee $1.77", while Claude AND Qwen both capture the fee and the true Payment Total of $63.03. Azure is short by $9.19.

The second structural fact: a Reconciler exists and IS wired to production (ReceiptSnapshotApplying.swift:273-274 writes Receipt.reconciliationSeverity; ReconciliationChip + ReceiptDetailView.swift:191 surface it) — but it reconciles ONLY arithmetic (sum-of-items vs subtotal; subtotal+extras vs total, Reconciler.swift:54-82) with hardcoded USD-dollar thresholds (matchThreshold=0.01, warnThreshold=0.05, Reconciler.swift:34-35). It completely ignores the confidence fields that the mapper DOES populate (ScannedReceipt.swift:81,103). And the chip is advisory — a warn/error chip never blocks the split (ReceiptDetailView.swift:286-294). So a garbled-but-arithmetically-consistent receipt splits clean with zero warning.
